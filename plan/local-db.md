# แผนเพิ่มคลังเพลงในเครื่องสำหรับค้นหาแบบทันที

สถานะ: **อนุมัติและพัฒนาในเครื่องแล้ว (2 ตุลาคม 2569)** — ยังไม่ได้ push หรือ deploy; ยังควรทดสอบประสิทธิภาพบนโทรศัพท์จริงก่อนเปิดใช้กว้าง

## เป้าหมายและขอบเขต

- ให้ผู้ใช้เลือกค้นหาจาก **Supabase** หรือ **ในเครื่อง** ได้ โดยค่าเริ่มต้นยังเป็น Supabase
- โหมดในเครื่องเป็นการสมัครใจ: ดาวน์โหลดเฉพาะ *ข้อมูลเพลง* ที่จำเป็นต่อการค้นหา เช่น ชื่อเพลง ศิลปิน YouTube video ID ข้อมูลช่อง URL รูปปก และวันหมดอายุของรายการ ไม่ดาวน์โหลดวิดีโอ เสียง หรือไฟล์รูปปก
- หลังเตรียมข้อมูลสำเร็จ การพิมพ์ค้นในโหมดเครื่องต้องไม่รอ Supabase หรือ YouTube; ผลข้อความควรปรากฏเกือบทันที ส่วนรูปปกอาจยังโหลดจากอินเทอร์เน็ต
- Supabase ยังคงเป็นแหล่งข้อมูลหลัก การเพิ่มเข้าคิวและการเล่นเพลงยังเป็นระบบออนไลน์เดิม ไม่ใช่ระบบเล่นแบบออฟไลน์
- ไม่เปลี่ยนพฤติกรรมการแสดงเพลงยอดนิยมครั้งละ 50 รายการและการเลื่อนโหลดเพิ่ม
- ระยะแรกไม่ทำไฟล์ `.exe` และไม่เพิ่มบริการแบบเสียเงิน

## สภาพปัจจุบันที่แผนนี้อ้างอิง

- หน้า `src/app/join/[code]/page.tsx` แสดงผลล่วงหน้าจากแคชคำค้น/เพลงตั้งต้น แล้วหน่วง 280 ms ก่อนค้นคลังผ่าน `/api/search` ซึ่งอาจมีงานอัปเดตข้อมูลประกอบ
- มี `/api/catalog?q=...` สำหรับค้นคลังแบบอ่านอย่างเดียวอยู่แล้ว แต่หน้า Join ยังไม่ได้ใช้เป็นทางหลักระหว่างพิมพ์
- ตาราง `karaoke_catalog` อยู่ใน Supabase และเข้าถึงด้วยคีย์ลับฝั่งเซิร์ฟเวอร์เท่านั้น; ฝั่งเบราว์เซอร์ไม่ควรติดต่อฐานข้อมูลด้วยคีย์นี้โดยตรง
- จำนวนข้อมูลที่ตรวจในช่วงวางแผนอยู่ราว 17,988 แถวที่ยังไม่หมดอายุ ตัวเลขจริงตอนดาวน์โหลดอาจเปลี่ยน และบางแถวอาจถูกตัดด้วยกฎคัดกรองของแอป
- ตัวอย่างข้อมูล 100 แถวให้ขนาด JSON ประมาณ 53 KB จึงประเมินเบื้องต้นว่าข้อมูลทั้งชุดอยู่ระดับหลาย MB (ราว 9 MB ก่อนบีบอัด) ไม่ใช่ขนาดที่รับประกัน

## Phase 0 — วัดฐานและกำหนดสัญญาข้อมูล

**งาน**

1. วัดเวลาค้นจริงของหน้า Join ปัจจุบันบนเครื่องคอมและโทรศัพท์ตัวอย่าง: จากพิมพ์ตัวอักษรจนเห็นผลข้อความ แยกเวลา debounce, API และ render
2. ยืนยันจำนวนเพลงที่ใช้ค้นได้จริง ขนาดข้อมูลต่อรายการ และฟิลด์ขั้นต่ำที่ UI/การจัดอันดับต้องใช้ ไม่ส่ง `payload` ทั้งก้อนโดยไม่จำเป็น
3. กำหนดกฎเดียวกันสำหรับเพลงที่โหลดได้: `embeddable`, ยังไม่หมดอายุ, รูปแบบข้อมูลถูกต้อง, และไม่ติดกฎตัดชื่อเพลงของแอป
4. กำหนดรูปแบบข้อมูล export พร้อม `schemaVersion`, เวลาสร้างข้อมูล, `video_id` และ `expires_at` เพื่อรองรับการเปลี่ยนรูปแบบภายหลัง
5. ตกลงตัวชี้วัดความเร็วและชุดคำค้นทดสอบภาษาไทย/อังกฤษ รวมถึงคำที่ไม่พบ ก่อนเริ่มเปลี่ยนพฤติกรรมหน้าเว็บ

**เกณฑ์ผ่าน:** มีตัวเลขฐานที่วัดซ้ำได้และสัญญาข้อมูลที่ทดสอบได้; ไม่ต้องเปลี่ยน schema Supabase ใน Phase นี้

## Phase 1 — เร่งโหมด Supabase ปัจจุบัน

**งาน**

1. เปลี่ยนการค้น *ระหว่างพิมพ์* ที่หน้า Join ไปใช้ `/api/catalog` แบบอ่านอย่างเดียว ไม่เรียก YouTube และไม่รอการอัปเดตยอดวิว
2. คงการหน่วงสั้น ๆ เพื่อไม่ส่งคำขอทุกตัวอักษร แต่ใช้ `AbortController` ยกเลิกคำขอเก่าและป้องกันผลคำค้นเก่าทับคำค้นใหม่
3. คงการค้น YouTube เมื่อกด Enter แล้วตรวจคลังไม่พบ และปุ่มค้น YouTube โดยตรง; หาก Supabase ล่มต้องไม่สรุปว่า “ไม่มีเพลง” แล้วใช้โควตา YouTube อัตโนมัติ
4. แยกผลค้นเพลงออกจากรายการยอดนิยมที่โหลดเพิ่มทีละ 50 ตามเดิม

**เกณฑ์ผ่าน:** ขณะพิมพ์ไม่เกิดคำขอ YouTube/งานรีเฟรชยอดวิว ผลใหม่ไม่ถูกผลเก่าทับ และพฤติกรรม Enter/ปุ่ม YouTube ยังถูกต้อง

## Phase 2 — API ส่งออกข้อมูลคลังเป็นชุด

**งาน**

1. เพิ่ม endpoint ฝั่งเซิร์ฟเวอร์แบบอ่านอย่างเดียวสำหรับดาวน์โหลดข้อมูลเพลงที่อนุญาตเท่านั้น คีย์ Supabase/service role อยู่บนเซิร์ฟเวอร์เสมอ
2. แบ่งข้อมูลเป็นชุดจำกัดขนาด เช่น ชุดละ 500 แถว และใช้ cursor ตาม `video_id` แทน `OFFSET` สำหรับการอ่านลึก; กำหนดเพดาน `limit` และตรวจรูปแบบ cursor ทุกคำขอ
3. ส่งเฉพาะฟิลด์ที่ UI และการค้นต้องใช้ รวมถึงวันหมดอายุ ไม่ส่งข้อมูลห้อง สมาชิก คีย์ หรือข้อมูลภายในอื่น
4. ส่ง cursor ถัดไปและสถานะ `hasMore`; ควบคุมข้อผิดพลาด/time-out ให้ไคลเอนต์หยุดหรือเริ่มใหม่ได้ ไม่สร้างข้อมูลชุดครึ่งเดียวให้ใช้งาน
5. วัดจำนวนคำขอ ขนาดข้อมูลจริง และเวลาส่งครบชุด; ตรวจผลกระทบต่อโควตาแบนด์วิดท์ของโฮสต์และ Supabase

**ข้อแลกเปลี่ยนที่ต้องรับรู้:** endpoint นี้ทำให้ผู้เข้าชมดาวน์โหลด *ข้อมูลเพลงสาธารณะ* จำนวนมากได้ จึงต้องจำกัดฟิลด์และขนาดคำขออย่างเข้มงวด แต่ไม่สามารถถือว่ารายการชื่อเพลงเป็นความลับได้

**เกณฑ์ผ่าน:** อ่านครบโดยไม่มี `video_id` ซ้ำ/หายจากการแบ่งหน้า, ไม่มีเพลงที่ไม่ผ่านกฎคัดกรอง, ไม่มีคีย์ลับรั่ว และไม่แตะ YouTube API

## Phase 3 — จัดเก็บในเบราว์เซอร์และอัปเดตอย่างปลอดภัย

**งาน**

1. ใช้ IndexedDB ไม่ใช้ `localStorage` สำหรับข้อมูลทั้งคลัง เพราะจำนวนรายการมาก; เก็บแยกตาม browser profile และ origin (`localhost` กับเว็บจริงเป็นคนละชุด)
2. ผู้ใช้กด “ดาวน์โหลดคลัง” เองก่อนใช้โหมดเครื่อง แสดงจำนวน/ขนาดประมาณ ความคืบหน้า ปุ่มยกเลิก และข้อความว่าไม่ได้ดาวน์โหลดเสียงหรือวิดีโอ
3. ดาวน์โหลดข้อมูลเข้าสู่ชุดชั่วคราว ตรวจจำนวน/รูปแบบ/เวอร์ชัน แล้วจึงสลับตัวชี้ไปยังชุดใหม่เมื่อสำเร็จทั้งหมด หากยกเลิก เน็ตหลุด หรือพื้นที่ไม่พอ ให้ชุดเดิมยังใช้ได้
4. มีปุ่ม “อัปเดตคลัง” แบบผู้ใช้สั่งเองและ “ลบข้อมูลในเครื่อง”; แสดงจำนวนเพลง เวลาที่อัปเดต และคำเตือนเมื่อข้อมูลเก่า
5. กรองรายการที่ `expires_at` ผ่านไปแล้วขณะค้น และเตรียมทางกลับไปใช้ Supabase เมื่อไม่มีชุดข้อมูลที่ใช้งานได้
6. เก็บค่าที่ผู้ใช้เลือกโหมดเครื่องไว้เฉพาะเมื่อมีชุดข้อมูลสมบูรณ์; หากเบราว์เซอร์ล้างข้อมูลหรือขับข้อมูลออก ให้กลับโหมด Supabase พร้อมแจ้งเหตุผล

**หมายเหตุ:** การอัปเดตแบบทำชุดใหม่อาจใช้พื้นที่ชั่วคราวใกล้เคียงสองชุด ต้องตรวจพื้นที่/จัดการ quota และทดสอบจริงบนมือถือ ระยะแรกยังไม่ทำการซิงก์ส่วนต่างหรือลบข้อมูลเก่าแบบ background โดยอัตโนมัติ

**เกณฑ์ผ่าน:** ปิด/เปิดหน้าใหม่แล้วข้อมูลยังค้นได้ ดาวน์โหลดล้มเหลวไม่ทำลายชุดเดิม และผู้ใช้ลบข้อมูลในเครื่องได้จริง

## Phase 4 — ค้นหาในเครื่องแบบตอบสนองเร็ว

**งาน**

1. เมื่อเลือกโหมดเครื่อง ให้อ่านข้อมูลและเตรียมข้อความค้นที่ normalize แล้วเพียงครั้งเดียว ส่งงานสร้างดัชนี/จัดอันดับไปยัง Web Worker เพื่อไม่ให้ช่องพิมพ์ค้าง
2. ค้นทันทีเมื่อพิมพ์โดยไม่เรียก API สำหรับคำค้น แสดงผลที่ตรงที่สุดก่อน เช่น 25 รายการแรก พร้อมใช้กฎความเกี่ยวข้องและกฎคัดกรองเดียวกับคลังหลักให้มากที่สุด
3. ใช้เลขลำดับคำขอใน Worker เพื่อทิ้งผลของคำค้นเก่าที่ตอบช้ากว่า; รองรับคำไทยที่มีสระ/วรรณยุกต์ คำบางส่วน ภาษาอังกฤษ และช่องว่างตามชุดทดสอบ
4. หากข้อมูลยังโหลดจาก IndexedDB หรือ Worker ยังสร้างดัชนีไม่เสร็จ ให้แสดงสถานะชัดเจน ไม่กล่าวอ้างว่าพร้อมค้นในเครื่องแล้ว
5. หากโหมดเครื่องไม่พบเพลง เมื่อกด Enter ให้ตรวจ Supabase หนึ่งครั้งก่อนใช้ขั้นตอนค้น YouTube เดิม เพราะสำเนาในเครื่องอาจล้าสมัย; ถ้าออฟไลน์ให้แจ้งว่าไม่สามารถตรวจออนไลน์ได้
6. ตรวจความถูกต้องของเพลงจากข้อมูลล่าสุดก่อนเพิ่มเข้าคิวตามกลไกที่มีอยู่ เพื่อไม่ให้เพลงที่ถูกลบ/หมดอายุในสำเนาเก่าเข้าคิวโดยไม่ตั้งใจ

**เกณฑ์ผ่าน:** การพิมพ์ในโหมดเครื่องไม่มีคำขอค้นไป Supabase/YouTube, UI ไม่ค้าง, ผลลัพธ์ไม่สลับย้อนคำค้น และลำดับค้นออนไลน์สำรองทำงานตามที่กำหนด

## Phase 5 — UX, ทดสอบครบเส้นทาง และเปิดใช้

**งาน**

1. วางตัวเลือก `Supabase | ในเครื่อง` ใกล้ช่องค้นหา โดย Supabase เป็นค่าเริ่มต้น และปุ่มในเครื่องพาไปดาวน์โหลดเมื่อยังไม่มีข้อมูล
2. ทดสอบสลับโหมด รีโหลดหน้า ดาวน์โหลด/ยกเลิก/อัปเดต/ลบข้อมูล เน็ตหลุด พื้นที่ไม่พอ แคชล้าสมัย การเพิ่มคิว และการเล่นเพลง
3. วัดเวลาจริงกับคลังขนาดเต็มบนคอมและมือถือ ทั้งค้นครั้งแรกหลังเปิดหน้าและค้นครั้งถัดไป; ตั้งเป้าผลข้อความภายในประมาณ **0.1–0.2 วินาทีหลังพิมพ์เมื่อดัชนีพร้อมแล้ว** ไม่รับประกันทุกเครื่อง
4. ตรวจว่า Phase 1 เร็วกว่าค่าฐาน, Phase 4 ไม่มี network search ระหว่างพิมพ์, endpoint ส่งออกไม่เผยข้อมูลที่ไม่ควรเผย และการค้น YouTube ไม่เพิ่มการใช้โควตาโดยไม่ตั้งใจ
5. เปิดใช้แบบค่อยเป็นค่อยไปและเก็บข้อผิดพลาด/ค่าประสิทธิภาพที่ไม่บันทึกคำค้นหรือข้อมูลส่วนตัวเกินจำเป็น; หากมีปัญหา ผู้ใช้สลับกลับ Supabase ได้ทันที

**เกณฑ์ผ่านสุดท้าย:** ผู้ใช้สามารถเลือกดาวน์โหลดข้อมูลเพลง ค้นในเครื่องได้จริงแบบตอบสนองเร็ว และกลับไปค้นออนไลน์ได้ โดยระบบคิว/เล่นเพลงและรายการยอดนิยมเดิมไม่เสีย

## สิ่งที่ยังไม่ทำในแผนนี้

- ดาวน์โหลดหรือเก็บวิดีโอ/เสียง YouTube ในเครื่อง และการเล่นเพลงแบบออฟไลน์
- ทำแอปติดตั้ง `.exe`
- ซิงก์ข้อมูลส่วนต่างอัตโนมัติหรือดาวน์โหลดคลังใหม่เงียบ ๆ ทุกครั้งที่เปิดหน้า
- รับประกันว่าเพลงใหม่จะอยู่ในคลังเครื่องทันทีโดยไม่กดอัปเดต
- เปลี่ยน schema/RLS ของ Supabase โดยไม่มีเหตุจำเป็น; หาก Phase ปฏิบัติพบว่าต้องเปลี่ยน จะเสนอแยกพร้อมเหตุผลก่อน

## จุดตัดสินใจก่อนเริ่มลงมือ

ผู้ใช้อนุมัติแผนแล้ว จึงเริ่มดำเนินการ Phase 0 → 5 โดยไม่แก้ schema/RLS ของ Supabase และไม่ดาวน์โหลดสื่อ YouTube

## บันทึกผลการพัฒนาในเครื่อง (2 ตุลาคม 2569)

- Phase 0: ตรวจเส้นทางเดิมที่หน่วง 280 ms ก่อนเรียก API; วัด API อ่านคลัง `/api/catalog` ได้ประมาณ 443 ms ในหนึ่งคำค้นหลังเปิดเซิร์ฟเวอร์ ไม่ได้เก็บค่า *ก่อนแก้* ครบทุกอุปกรณ์ จึงไม่ใช้เป็นข้ออ้างว่าเร็วขึ้นกี่เท่า
- Phase 1: หน้า Join เรียก `/api/catalog` ระหว่างพิมพ์แทน `/api/search`; ทดสอบในเบราว์เซอร์แล้วไม่มีคำขอ YouTube ระหว่างพิมพ์
- Phase 2: API `/api/catalog/export` อ่านทีละ 500 แถวด้วย cursor `video_id`, คัดเฉพาะเพลงใช้ได้และส่งฟิลด์ที่อนุญาต; `/api/catalog/verify` ตรวจเพลงในคลังปัจจุบันก่อนเพิ่มเพลงจากผลค้นในเครื่องเข้าคิว
- Phase 3: ดาวน์โหลดลง IndexedDB สำเร็จ **13,965 เพลงที่ผ่านการคัดกรอง** ในเบราว์เซอร์ทดสอบ; รีโหลดแล้วยังใช้ได้ การจำลองให้อัปเดตล้มเหลวหลังดาวน์โหลดบางส่วนยังเก็บชุดเดิมครบและลบข้อมูลชั่วคราว
- Phase 4: ค้นด้วย Web Worker โดยไม่ส่งคำค้นไปเครือข่าย; คำว่า “ขอบฟ้า” ได้ 14 ผลและวัดจากการเปลี่ยนค่า input ถึงผลข้อความบนคอมทดสอบได้ประมาณ **33 ms**; จำลองออฟไลน์แล้วยังค้นข้อความได้
- Phase 5: ทดสอบหน้า Join ขนาดหน้าจอ 390×844 และหน้าแรก ไม่มี error overlay; `npm test` ผ่าน 47 รายการ, `npm run build` และ TypeScript ผ่าน, lint ไม่มี error (ยังมี warning เดิมในโครงการ) ยังไม่ได้ทดสอบบนโทรศัพท์จริงหรือ deploy
- ขยายไปหน้า `/player`: ใช้ IndexedDB และ Web Worker ชุดเดียวกับหน้า Join, มีตัวเลือก Supabase/ในเครื่องและหน้าจัดการคลัง, ค้นทันทีระหว่างพิมพ์, ตรวจคลังออนไลน์ก่อนเพิ่มเพลงจากผลในเครื่องเข้าคิว, และคงการค้น Supabase → YouTube เมื่อในเครื่องไม่พบเพลง ทดสอบในเบราว์เซอร์ว่าโหมดในเครื่องไม่มีคำขอ API ระหว่างพิมพ์/สลับการเรียง, รีโหลดยังจำโหมด, และสลับกลับ Supabase แล้วเรียก `/api/catalog` ได้
- เพิ่มประสิทธิภาพการจัดอันดับโดยคำนวณคะแนนความตรง/คาราโอเกะ/ช่องทางการครั้งเดียวต่อเพลงก่อนเรียง แทนการคำนวณซ้ำในตัวเปรียบเทียบ; ทดสอบเทียบลำดับเดิมทั้งโหมดชื่อเพลงและศิลปิน บน `/player` กับคลัง 13,965 เพลง คำกว้าง “รัก” จากราว 1.5 วินาทีเหลือมัธยฐาน 102 ms (p95 106 ms จาก 30 รอบ) และ “ใจ” เหลือมัธยฐาน 95 ms (p95 100 ms) ในเบราว์เซอร์ทดสอบ ไม่พบคำขอ API ระหว่างพิมพ์; ยังไม่ได้วัดบนโทรศัพท์จริง
