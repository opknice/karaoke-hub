# ออกแบบ Karaoke Hub สำหรับ Android TV ผ่าน Capacitor

วันที่: 23 ตุลาคม 2026 (Asia/Bangkok)

สถานะ: ผ่าน builder check แล้ว (ไม่มีคำถามสำคัญค้างจากผู้ตรวจ) รอผู้ใช้ตรวจและอนุมัติแบบ ยังไม่เริ่มเขียนโค้ดผลิตภัณฑ์

## เป้าหมายและสิ่งที่ผู้ใช้ยืนยัน

ปรับแอปเดิมให้ติดตั้งและใช้งานบน Xiaomi TV Box รุ่น MiTV-AFKR0 ตามข้อมูลจากผู้ใช้: Android TV 11, build RTT0.211222.001.772 release-keys โดยไม่ใช้คีย์บอร์ด

- ต่อผ่าน Capacitor และใช้ Next.js กับระบบห้อง/เพลง/คิวเดิม
- เมื่อเปิดแอปคาราโอเกะอยู่ กดปุ่ม Google Assistant บนรีโมทแล้วพูดชื่อเพลงได้ทันที ไม่ต้องเลือกปุ่มไมค์ในแอปก่อน
- เมื่อพบหลายเพลง ใช้ปุ่มทิศทางและ OK บนรีโมทเลือกเพลง
- แสดง QR สำหรับให้มือถือเข้าห้อง ค้นหาเพลง และเพิ่มเพลงเข้าคิว
- มือถือทุกเครื่องที่เข้าห้องแล้วมีสิทธิ์เล่นต่อ/พักเพลง/ข้ามเพลงที่ทีวีกำลังเล่น

ความสำเร็จต้องพิสูจน์กับรีโมทและกล่องจริง การรับ intent ที่จำลองผ่าน ADB เพียงอย่างเดียวไม่ถือว่าผ่านการค้นหาด้วย Assistant

## Approaches — ทางเลือกและข้อสรุป

1. **ต่อยอดผ่าน Capacitor (ผู้ใช้เลือก):** ใช้หน้าเว็บและระบบข้อมูลร่วมกับมือถือ เพิ่มส่วน native เท่าที่ Android TV ต้องใช้ และปรับการนำทางด้วยรีโมท ลดงานเขียนซ้ำ แต่ต้องจัดการ WebView, focus และการรับคำค้นข้าม native/web ให้ถูกต้อง
2. **สร้าง Android TV native แยก:** ควบคุม UI ทีวีได้โดยตรง แต่ต้องพัฒนาหน้าทีวีใหม่และดูแลคู่กับเว็บมือถือ จึงไม่ใช่แนวทางที่ผู้ใช้เลือก

ทั้งสองทางเลือกยังต้องพิสูจน์การทำงานกับ Assistant ของ Xiaomi ไม่ได้ทำให้ปุ่ม Assistant กลายเป็นปุ่มของแอปโดยอัตโนมัติ

## สภาพโค้ดปัจจุบันที่ตรวจแล้ว

- `capacitor.config.ts` ใช้ app ID `com.karaokehub.app` และโหลด `https://karaoke-hub-nu.vercel.app/player`; APK ต้องเชื่อมอินเทอร์เน็ต
- `android/app/src/main/java/com/karaokehub/app/MainActivity.java` เป็น `BridgeActivity` เปล่า ยังไม่มีการรับคำค้นหรือ plugin ค้นหา
- Android manifest มี launcher ปกติและสิทธิ์อินเทอร์เน็ต ยังไม่มี TV launcher/search configuration
- `src/components/PlayerSearchOverlay.tsx` มีค้นหาเพลง เลื่อนผลลัพธ์ขึ้น/ลง และ Enter เพื่อเพิ่มเพลง แต่หลายส่วนดึง focus กลับเข้าช่องพิมพ์และใช้ keyboard shortcuts
- การเลือกผลการค้นหาเดิมเรียก `addToQueue`; ถ้ายังไม่มีเพลงเล่น ระบบคิวอาจเริ่มเพลงนั้น ถ้ามีเพลงเล่นอยู่ให้เพิ่มเข้าคิวตามกติกาเดิม
- หน้า `src/app/player/page.tsx` เตรียมห้องอัตโนมัติผ่าน `ensureActiveRoom` และแสดง QR ได้แล้ว
- `src/app/join/[code]/page.tsx` มีเข้าห้องด้วยชื่อเล่น ค้นหา เพิ่มเพลง และจัดการคิวของผู้เข้าร่วม แต่ยังไม่เรียกปุ่มควบคุมเล่น/พัก/ข้ามจากหน้านี้
- `KaraokeContext` มี `setRoomPlayback` และ `skipSong`; migration `20261001024319_shared_room_playback_controls.sql` มี RPC ที่ตรวจสมาชิกห้องและอนุญาตสมาชิกควบคุมเพลงอยู่แล้ว ต้องตรวจว่า deployment เป้าหมายลง migration นี้จริงก่อนทดสอบรวม
- สถานะการเล่นร่วมกันเก็บในฐานข้อมูลและรับผ่าน Supabase Realtime; `BroadcastChannel` ใช้กับแท็บในเครื่องเดียวกัน ไม่ใช่ช่องควบคุมระหว่างมือถือกับทีวี
- มีการแก้ไขค้างและไฟล์ Android/Capacitor ที่ยังไม่ถูก track ก่อนเริ่มงานนี้ ต้องรักษางานเหล่านั้นและไม่รวมเข้าคอมมิตเอกสารโดยอัตโนมัติ
- เครื่องพัฒนาพบ ADB และ Java 21 แล้ว แต่ `adb devices` ยังไม่พบอุปกรณ์ที่เชื่อมต่อ ณ ตอนเขียนแบบ จึงยังไม่อ้างว่าทดสอบกล่องหรือ Assistant แล้ว

## ข้อจำกัดที่ต้องแก้ด้วยหลักฐาน: Google Assistant

เอกสาร Android ระบุว่า `KEYCODE_ASSIST` เปิด global assist activity และไม่ส่ง event นี้ให้แอป จึงออกแบบให้ใช้การเชื่อมค้นหาที่ระบบรองรับ แทนการรอจับปุ่มนี้ใน JavaScript หรือ `dispatchKeyEvent`

ช่องทางที่ต้องทดลองคือ Android TV searchable activity, `searchable.xml`, search provider และ intent ที่ระบบส่งกลับ โดยยึดผลที่เกิดจริงบนกล่องเป็นข้อสรุป เอกสารเหล่านี้ไม่ใช่หลักประกันว่า Assistant เวอร์ชันบน Xiaomi จะส่งคำพูดทั่วไปกลับเข้าแอปที่เปิดอยู่โดยอัตโนมัติ

### ขั้นพิสูจน์ก่อนพัฒนาส่วนที่เหลือ

หลังอนุมัติแบบและแผน ให้ทำการทดสอบทางเทคนิคขนาดเล็กใน Android wrapper เดิมก่อน งานนี้เป็นหลักฐานความเป็นไปได้ ไม่ใช่คำรับรองว่าฟีเจอร์เสร็จแล้ว

1. ตรวจการเชื่อมต่อกล่อง เวอร์ชัน Assistant ภาษา และการติดตั้ง APK; หากยังเข้าถึงกล่องไม่ได้ ให้เตรียม APK กับขั้นตอนทดสอบและคงสถานะว่ายังไม่ผ่านขั้นนี้
2. ทดสอบ searchable configuration และ provider ที่รองรับการค้นหาขณะอยู่ในแอป ตรวจ action, query และลำดับ lifecycle ที่เกิดจริง
3. ทดสอบกด Assistant แล้วพูดชื่อเพลงภาษาไทยโดยไม่ต้องบอกชื่อแอป ไม่ต้องกดไมค์ในแอป และไม่ต้องเปิดคีย์บอร์ด
4. คำค้นต้องกลับเข้า Karaoke Hub พร้อมให้เลือกหลายผลลัพธ์ด้วยรีโมทได้ การเห็น Assistant เปิดหรือผลลัพธ์ไปอยู่ใน YouTube อย่างเดียวไม่ผ่าน
5. ตรวจการออกจากแอปแล้วกด Assistant: โครงการนี้ไม่เพิ่มประสบการณ์ค้นหา Karaoke Hub จากหน้าหลัก Android TV และไม่ควรบังคับเปิดแอปจากการค้นหาทั่วไปข้างนอกแอป
6. บันทึกกล่อง/build, เวอร์ชัน Assistant, ภาษา, ขั้นตอน, intent และผลทดสอบ โดยไม่เก็บเสียงหรือ token ลง log

ถ้าทางที่ระบบรองรับไม่ให้พฤติกรรมตามข้อกำหนด ให้รายงานสิ่งที่ทดลองและข้อจำกัด แล้วขอให้ผู้ใช้ตัดสินใจเรื่องเปลี่ยนวิธีใช้งานก่อนดำเนินงานส่วนที่พึ่งพาเสียงต่อ ห้ามแทนด้วยปุ่มไมค์ในแอป การบอกชื่อแอปทุกครั้ง การ remap ปุ่ม หรือการใช้ Accessibility/root โดยถือว่าผู้ใช้ยอมรับแล้ว

การซ่อน `includeInGlobalSearch` หรือการตรวจเพียง `onResume` ไม่ใช่หลักฐานว่าค้นหาได้เฉพาะตอนเปิดแอป: Assistant อาจทำให้ activity พักชั่วคราว ต้องทดสอบทั้งการรับคำค้นและขอบเขตการเรียกจริงก่อนล็อกวิธีเชื่อม ส่วนวิธีและค่าตั้งสุดท้ายให้ผู้พัฒนาเลือกจากผลขั้นพิสูจน์นี้

## การแบ่งส่วนระบบ

### Android / Capacitor

- เพิ่มคุณสมบัติ Android TV: TV launcher/banner, landscape และประกาศว่าไม่ต้องมี touchscreen โดยอิงข้อกำหนดและ SDK ที่ติดตั้งจริง
- ใช้ส่วน native รับเฉพาะ action/query/ตัวระบุผลลัพธ์ที่ตรวจสอบแล้ว จากนั้นส่งข้อมูลที่เป็นโครงสร้างให้เว็บผ่าน Capacitor plugin
- เตรียม listener/readiness handshake: เก็บคำค้นล่าสุดที่ยังไม่ได้ส่งในหน่วยความจำระหว่างเว็บโหลด ส่งหลังเว็บพร้อม และตอบรับ request ID เพื่อไม่ค้นซ้ำเมื่อ resume/reload
- คำค้นใหม่ยกเลิกหรือแทนคำค้นเก่าที่กำลังประมวลผล ผลเก่าห้ามทับผลล่าสุด
- ตรวจ query ตามขอบเขต API เดิม 2–250 ตัวอักษรและตรวจ action/URI ที่รับเข้า ไม่ประกอบคำพูดเป็น JavaScript executable หรือเปิด URL ใดก็ได้
- ใช้ HTTPS origin ที่กำหนดไว้ในแอปสำหรับ WebView และ search API; ไม่ใส่ Supabase secret/service-role หรือ YouTube API key ใน APK
- หากต้องมี provider ให้ใช้ catalog/API สำหรับ metadata ที่จำเป็นและจำกัดเวลา/จำนวนผลลัพธ์ ไม่เรียก YouTube แบบเสีย quota ทุกครั้งที่ Assistant query provider
- ไม่ขอสิทธิ์บันทึกเสียงเพิ่มโดยอัตโนมัติ ถ้าใช้ Assistant เป็นผู้รับเสียงทั้งหมด

### หน้าเว็บสำหรับทีวี

- เปิดโหมดทีวีเมื่อ native wrapper แจ้ง platform/capabilities ที่ยืนยันแล้ว การตรวจขนาดหน้าจออย่างเดียวไม่เพียงพอ
- ใช้ผลค้นหาและ ranking เดิม โดย native ส่งคำค้นแล้วระบบเว็บค้นหาคลังให้อัตโนมัติ
- คำค้นเสียงเข้าสู่เส้นทางค้นหาเดียวกับการ submit เดิม; หากคลังไม่พบ ให้ใช้ fallback YouTube ตามกลไก quota/cache เดิม ไม่เรียกซ้ำจากทั้ง native และเว็บ
- ปรับการจัดการ focus สำหรับโหมดทีวี เลิก autofocus/แย่ง focus กลับช่องพิมพ์ตลอดเวลา และไม่เปิด on-screen keyboard ในงานหลัก
- ทุกการกระทำหลักเข้าถึงได้ด้วย D-pad/OK/Back: เลือกผลค้นหา เปิดคิว เล่น/พัก ข้าม เปิด QR ปิดแผง และลองใหม่เมื่อเกิดข้อผิดพลาด
- ให้เห็นรายการที่เลือกและเลื่อนรายการตาม focus ใช้ตัวอักษรและพื้นที่กดที่อ่านจากระยะทีวีได้ โดยรายละเอียดภาพให้ผู้พัฒนาเสนอภายในขอบเขตนี้
- Back ปิดแผงที่เปิดอยู่ก่อนและคืน focus ไปจุดเดิม; เมื่อไม่มีแผงให้กลับตามวงจร Android ตามปกติ
- OK ที่ผลค้นหาเพิ่มเพลงตามพฤติกรรมคิวเดิม พร้อมข้อความสำเร็จหรือข้อผิดพลาด กดค้าง/กดซ้ำระหว่างเพิ่มห้ามส่งเพิ่มซ้ำ
- OK ที่เพลงในแผงคิวยังคงความหมายเล่นเพลงนั้นตามพฤติกรรมเดิม ป้ายกำกับต้องแสดงความแตกต่างจากเพิ่มเพลงให้ชัด
- จัดการ YouTube iframe ไม่ให้ขโมย navigation ของแอป และทำให้ปุ่มเริ่มเล่นเมื่อ autoplay ถูกบล็อกเข้าถึงด้วยรีโมทได้
- ความสามารถที่พึ่ง Chrome extension เช่นตัดเสียงร้องหรือ tempo บางแบบ ต้องตรวจ capabilities บน Android; ไม่แสดงว่าทำงานได้เพียงเพราะเวอร์ชัน desktop มีส่วนนี้

### มือถือผ่าน QR

- ใช้ URL `/join/{roomCode}` และขั้นตอนใส่ชื่อเล่น/เข้าห้องเดิม ไม่ต้องติดตั้งแอปมือถือเพิ่ม
- เพิ่มชุดควบคุมเพลงปัจจุบัน: เล่นต่อ พัก และข้าม พร้อมชื่อเพลงและสถานะที่รับจากห้อง
- ปุ่มแสดงได้สำหรับสมาชิกทุกคน ใช้ `setRoomPlayback(true/false)` และ `skipSong()` ผ่านระบบสิทธิ์สมาชิกเดิม ไม่ใช้ `setIsPlaying` อย่างเดียวซึ่ง broadcast ได้เฉพาะเครื่อง
- ขณะส่งคำสั่งปิดปุ่มชั่วคราวและแสดงผลลัพธ์; เมื่อไม่มีเพลงปัจจุบัน ปิดปุ่มที่ใช้ไม่ได้
- การพักคือ pause/resume ที่ตำแหน่งเดิม การข้ามไปเพลงถัดไปใช้คิวเดิม; ถ้าคิวหมดให้กลับสถานะว่าง
- รักษาการค้นหา เพิ่มคิว และการจัดการคิวของตัวเองตามที่มีอยู่ ไม่ขยายสิทธิ์ลบคิวคนอื่นโดยปริยาย

### ข้อมูลร่วมกันและการเชื่อมต่อใหม่

- ฐานข้อมูลห้องเป็นแหล่งอ้างอิงร่วม ใช้ RPC ที่ตรวจ membership จริง ไม่ถือว่าทราบ room code อย่างเดียวเท่ากับได้รับสิทธิ์ควบคุม
- ใช้ `p_expected_playing_id` และ transaction/lock เดิมป้องกันการข้ามซ้อนจากสองมือถือหรือ pause เพลงใหม่ด้วยหน้าจอเก่า
- ลำดับคำสั่งเล่น/พักยึดลำดับที่ฐานข้อมูลยอมรับ แล้วทุกหน้าจอ refresh เป็นสถานะล่าสุด
- หลัง reconnect/resume โหลดคิวและสถานะห้องใหม่ก่อนเปิดควบคุม; คำสั่งที่ยืนยันไม่ได้ห้ามค้างในคิวเพื่อ replay ข้ามเพลงภายหลัง
- คง subscription/refetch และรูปแบบ guest identity เดิม ตรวจการ reconnect บนเครื่องจริง ไม่เปิด player เสียงบนหน้ามือถือ
- ขั้นเริ่มต้นใช้ schema/RPC เดิม หากพบว่า deployment ขาด migration หรือจำเป็นต้องปรับ schema ให้ระบุเป็นงานแผนและตรวจสิทธิ์ตาม Supabase skill ก่อนดำเนินการ

## ข้อเสนอของผู้ออกแบบที่ขอให้ตรวจพร้อมเอกสาร

รายการต่อไปนี้เป็นการเลือกจากโค้ดและเป้าหมาย ไม่ใช่คำยืนยันเพิ่มเติมจากผู้ใช้:

1. คง OK ที่ผลค้นหาเป็นการเพิ่มคิว และให้ระบบเดิมเริ่มเพลงเมื่อไม่มีเพลงเล่นอยู่
2. คง APK แบบโหลดเว็บที่โฮสต์ผ่าน HTTPS จึงยังต้องใช้อินเทอร์เน็ต ไม่เพิ่มระบบเล่นเพลงออฟไลน์
3. ใช้ชื่อเล่นและการเข้าห้องผ่าน QR แบบเดิม; มือถือควบคุมได้หลังเข้าห้องสำเร็จ
4. ใช้ Back ปิดแผงก่อนออกจากหน้า และใช้กติกาคำสั่งชนกันของฐานข้อมูลเดิม
5. ทดสอบเสียงบนกล่องจริงก่อนขยายงานเต็ม หากทำไม่ได้ตามข้อกำหนดจะนำหลักฐานกลับมาให้ตัดสินใจ

## สิ่งที่ไม่รวมและสิ่งที่ถือว่าล้มเหลว

- ไม่สร้าง native UI ทั้งแอปใหม่ ไม่เปลี่ยนแหล่งวิดีโอ และไม่เพิ่มการเผยแพร่ผ่าน Play Store ในขอบเขตนี้
- ไม่เพิ่มการเลือกเพลงด้วยเสียงต่อเนื่อง เช่น “เลือกเพลงที่สอง” เพราะผู้ใช้เลือก D-pad/OK
- ไม่เพิ่มการค้นหา Karaoke Hub จากหน้าหลัก Android TV เป็นฟีเจอร์
- ไม่สร้างระบบ cloud speech recognition แยก หรือ remap ปุ่ม/ใช้ root/Accessibility เพื่อเลี่ยง Assistant โดยไม่ได้ตกลงใหม่
- ถือว่าล้มเหลวหากงานหลักต้องใช้คีย์บอร์ด, กด Assistant แล้วคำค้นไม่กลับเข้าแอป, โฟกัสหลงจนเลือกต่อไม่ได้ หรือมือถือเปลี่ยนเพลงผิดห้อง/ข้ามหลายเพลงจากคำสั่งเดียว

## การตรวจรับ

### ตรวจอัตโนมัติตามขอบเขตที่แก้

- ทดสอบการแปลง/ตรวจข้อมูลคำค้น การส่ง pending request ครั้งเดียว และผลค้นหาเก่าไม่ทับใหม่
- ทดสอบ D-pad/OK/Back สำหรับผลลัพธ์ คิว ปิดแผง และป้องกันการเลือกซ้ำ โดยตรวจพฤติกรรมผู้ใช้แทนการจับข้อความใน source
- ตรวจชุดควบคุมมือถือว่าคำสั่งใช้ห้องและเพลงที่ถูกต้อง พร้อมสถานะรอและข้อผิดพลาด
- รัน test, lint และ Next build ที่เหมาะสม รวม Android debug build หลังแก้ Android; อ่านคู่มือใน `node_modules/next/dist/docs/` ก่อนเขียนโค้ด Next.js

### ตรวจรวมบนกล่องจริงและมือถือ

1. ติดตั้ง/เปิดจาก TV launcher ได้ สร้างหรือคืนห้องและแสดง QR โดยไม่ใช้คีย์บอร์ด
2. เปิดแอป กด Assistant พูดชื่อเพลงไทย แล้วเลือกรายการด้วยรีโมท ทำซ้ำได้ทั้งตอนว่างและมีเพลงเล่น
3. ค้นหาหลายครั้ง ยกเลิก Assistant หรือให้ Assistant ฟังไม่สำเร็จ แล้วกลับมาใช้รีโมทและเล่นเพลงต่อได้
4. ตรวจ OK เพิ่มคิวหนึ่งครั้ง, Back คืน focus, คิวว่าง และปุ่ม retry โดยไม่ใช้คีย์บอร์ด
5. มือถือสองเครื่องเข้าห้องเดียวกัน: ทุกเครื่องเพิ่มคิว เล่นต่อ พัก และข้ามได้ ทีวีเล่นและแสดงสถานะตรงกัน
6. ส่ง skip ของเพลงเดียวพร้อมกันจากสองมือถือ: เปลี่ยนเพียงเพลงเดียว; คำสั่งเก่าห้ามพัก/ข้ามเพลงถัดไป
7. ผู้ที่ยังไม่เข้าห้องหรือเป็นสมาชิกอีกห้องควบคุมห้องนี้ไม่ได้
8. ตัด/ต่อเครือข่ายและออก/เข้าแอป: คืนสถานะห้องล่าสุดโดยไม่ replay skip เก่าและไม่สร้างห้องใหม่โดยไม่จำเป็น
9. ตรวจการเล่น YouTube/การเริ่มเล่นที่ถูกบล็อกและการเปิด Assistant ระหว่างเพลง ไม่ถือว่าการ build ผ่านยืนยัน playback บน WebView แล้ว

ทดสอบการเปลี่ยนคิวกับห้องทดสอบที่แยกจากห้องใช้งานจริง บันทึกส่วนที่ยังไม่ทดสอบตามจริง การตรวจรับบนกล่องต้องมีผู้ใช้หรืออุปกรณ์ที่เชื่อมต่อได้ จึงอาจเป็นขั้นที่ต้องให้ผู้ใช้ช่วยภายหลัง

## งานที่เหลือให้ผู้พัฒนาตัดสินใจจากหลักฐาน

- วิธี integration กับ Assistant และการจำกัด invocation ที่ผ่านขั้นพิสูจน์, ชื่อ Capacitor plugin และโครงสร้าง request/ack
- การจัดวางแผงและ focus graph ภายในพฤติกรรมที่ระบุ พร้อมสี/ขนาดที่สอดคล้อง UI เดิม
- จำนวน/timeout/cache ของ metadata provider ตามพฤติกรรมระบบค้นหาจริง โดยห้ามเพิ่มการเสีย YouTube search quota ระหว่าง suggestion
- การทดสอบ Android ที่เหมาะกับเครื่องมือซึ่งติดตั้งอยู่ และการส่ง debug APK ให้ทดสอบ
- เวอร์ชันและการติดตั้งเว็บ/APK ที่ต้องตรงกันเพื่อรองรับ bridge; แสดงข้อความเมื่อเว็บกับ native ใช้ capabilities ไม่ตรงกัน
